# OseroGameAI Constitution

## Core Principles

### I. 要件を明確にしてから実装する

Spec Kitで要件・受け入れ条件を整理し、利用者へのインタビューを続ける。
ゲームの核、ルールの例外、対象環境、提供範囲に重大な曖昧さが残る間は実装に着手しない。
質問・回答・決定・未解決事項を docs/INTERVIEW_BOARD_REMIX.md 等の docs/INTERVIEW_*.md に保存し、回答ごとに関連仕様を更新する。

### II. 新しさを遊びの判断に結びつける

独自性は見た目だけでなく、プレイヤーが何を予測し、選ぶかとして定義する。
既存作との比較範囲を示し、世界初であると根拠なく断言しない。
利用者が選んでいないアイデアを採用済み仕様として扱わない。

### III. ゲーム状態と表示を分離する

PROAGENTS.mdの設計・コード規約を遵守する。
ルールを表示やAIに重複実装せず、状態の所有者を明確にする。
AIには思考上限と中断を設け、古い対局への計算結果適用を防ぐ。

### IV. 受け入れ条件で品質を検証する

合法手、反転、特殊ルール、パス、終局、勝敗を決定的に検証する。
実装時は影響に応じたテストと実環境での操作確認を行う。
未実行の検証や未達の条件を完了扱いにしない。

### V. 記録を更新し、コンテキストを節約する

各資料の正本を定め、決定の要点と参照先を保存する。
必要な工程のスキルと対象ファイルだけ読み、同じ説明や長い出力を繰り返さない。
コンテキスト節約を理由に必要なインタビューや検証を省略しない。

## 対象環境と素材

実装先はWeb、またはVisual Studio 2022とDirectXを用いるWindowsアプリとする。
最終選択と対応端末はインタビューで決定する。
画像は世界観の決定後に検索し、採用素材の出典・ライセンス・必要な帰属表示を記録する。

## 開発工程と品質ゲート

constitution → specify → clarify → plan → checklist → tasks → analyze → implementを基本とする。
利用者の「明確になるまでインタビューを続ける」という指示を優先し、質問数の既定上限で打ち切らない。
tasksへ進む前に、要件の要約と実装範囲を利用者へ提示し、明示的な確認を得る。
要件確定時には、対局開始から終了・再開始、特殊ルールの衝突、対戦形式、操作・画像・音声、
保存・失敗時の挙動、性能、対象環境、提供範囲を網羅し、検証可能な受け入れ条件を用意する。
ゲーム概要・実装済み・実装予定の資料は関連変更と同時に更新する。

## Governance

利用者の明示指示を優先する。本憲章は開発原則、PROAGENTS.mdは具体的な開発規約の正本。
矛盾は黙って解釈せず記録して解消する。変更時は理由、影響する仕様、日付、バージョンを更新する。
互換性を失う原則変更はMAJOR、原則追加はMINOR、意味を変えない修正はPATCHとする。
レビュー時に憲章・開発規約・受け入れ条件との整合を確認する。
